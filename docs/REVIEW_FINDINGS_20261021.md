Meter-history and retail controls explicitly reject `panic:` and reject the same probe.

The [isolated audit helper](evidence/20261021/seven-day-review/probe_mutation_failure_admission.py.txt) runs two tiny Go1.26.10 test functions outside the repository: an ordinary `t.Fatal` assertion and a panic. Both return exit1 and a named failure. It extracts and executes the exact three admission assertions from each of the six reviewed drivers, without executing any production mutation or replacing a test expectation. All six accept the ordinary assertion control; the four SQL/scope drivers also accept the panic, while meter-history/retail reject it. [Full observations and exact guards](evidence/20261021/seven-day-review/mutation-failure-admission-probe.json), [assertion output](evidence/20261021/seven-day-review/TestAuditAssertionFailure.log) and [panic output](evidence/20261021/seven-day-review/TestAuditPanickedControl.log) are retained. These are new synthetic Linux audit executions, not Windows execution or historical control reruns. No product or frozen test changed.

This establishes an admission weakness, not that a retained historical reversal actually panicked. Existing successful baseline tests, positive behavior checks and byte restoration evidence remain their own evidence. Historical drivers generally printed summaries rather than the complete rejected subprocess output, limiting retrospective assertion-versus-panic classification. Do not declare those historical controls invalid or independently proven assertion failures solely from the summary wording.

Recommended bounded follow-up: define one explicit mutation outcome contract covering compilation, the intended named assertion, panic/timeout/setup/infrastructure failures, exact restoration and a passing restored baseline. Independently test its admission with real compiler/assertion/panic outputs, then adopt it in separately reviewed driver changes while conserving every mutation identity and expectation. Retain bounded complete rejected-output evidence for auditability. Existing meter-history/retail panic rejection is a useful positive control, not proof that every other driver has identical safeguards. Until corrected, distinguish a named test failure from verified assertion-only reversal evidence. This finding does not justify a gate bypass, unrelated refresh or replay of old feature implementations.

The test resides in a disposable audit-probes worktree, not PR185; no existing expectation/production byte changed. Windows reproduction and a corrective candidate are not yet claimed.

The target specification says all include tags must match and tag names are case-insensitive. The primary page was fetched after search. Existing tests check ordinary case-insensitivity and exact values but do not cover colliding case-equivalent input keys. No existing finding covering this case was located in current failure/systematic-review records.

Recommended later correction: reject conflicting normalised filter keys before credential construction or scope discovery; define equal-value duplicates and provider tag collisions explicitly. Preserve ordinary single-key/source-equivalent semantics and all current tests. Independent literals should cover include/exclude, insertion order, same-value duplicates, exact value case and whitespace/Unicode normalisation policies before implementation. Pinned AZQR8e4f0577internal/models/filters.go was read completely and uses the same map-overwrite normalization. This is inherited source ambiguity; introduction within the last seven days is not established. Document a later rejection as a deliberate safety correction rather than source parity. Until corrected, avoid ambiguous tag-filter files. This is an acceptance risk, not an authorisation to silently widen scope or weaken checks.

No production, frozen input, expectation or existing test changed. Windows execution is not claimed.

Go1.26.10's local standard-library decode.go explicitly documents later duplicate keys replacing or merging earlier values and case-insensitive struct-field matching; current primary [encoding/json documentation](https://pkg.go.dev/encoding/json) corroborates v1 duplicate-name acceptance. Recommended deliberate follow-up: define strict comparison-input admission before projection, reject duplicate object names and conflicting aliases of known fields, enforce an explicit input-size/work budget, and retain the current healthy/identical-row/count-aggregation semantics. No evidence currently establishes that a retained historical comparison actually contained these ambiguities; do not relabel previous outcomes without checking their original bytes.
