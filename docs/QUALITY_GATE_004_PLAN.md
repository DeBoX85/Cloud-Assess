# Quality Gate 004 Plan: Core Validation Decision

Status: **planned; not passed**

This is the decision framework for the next core validation checkpoint. Quality Gates 001-003 are immutable reviews of earlier commits. A green CI run or a semantically equal report alone does not satisfy this gate.

## Intended decision

Decide whether the implemented generic scan is sufficiently characterized for a **defined first-release core scope**. The gate records an exact target commit, pinned source/APRL commits, CI runs, evidence bundle references, every accepted limitation, and the reviewer decision. It must not declare the toolkit release-ready: package installation, supply-chain material, licensing and final operational/security sign-off need a separate release gate.

Choose and document the first-release plugin and CLI boundary before passing Gate 004. An item may be implemented and validated or explicitly deferred in the target specification, implementation plan, README and ledger. A deferred item cannot silently appear as supported.

## Continuous checks supporting this decision

The Go quality workflow checks pinned provenance, formatting, module graph, branding, PowerShell validation helpers, build/help/version, race-enabled tests, aggregate statement coverage, vet and reachable known vulnerabilities. The Windows validation job adds native Windows PowerShell 5.1 parser/helper checks plus Go tests and executable help/version smoke tests. An active ruleset now requires pull requests and both job contexts on `bootstrap/core-v1`; the enforced development CI is not a Gate 004 or release PASS.

The 75% total coverage floor is a regression signal, not a release criterion by itself. Prioritize behavior-based tests in lower-covered risk areas such as throttling, discovery adapters, CLI composition, canonical result assembly and orchestration rather than raising one aggregate number without corresponding assertions.

## Focused checks before the Gate 004 decision

1. **Failed retrieval and bounded execution:** run deterministic denied-access, throttled/timeout, malformed-row, cancellation, and critical/noncritical-stage scenarios through the relevant Azure adapter and coordinator/application boundary. Check stage status, completeness, exit code, retained healthy records and report persistence. A failed retrieval must not pass as a valid empty dataset. The Cost access-denial cross-package test and truncated Diagnostics batch test cover two specific paths; other paths remain open.
2. **Diagnostics uncertainty:** retain the current non-success warning on partial batch failure. Correlate at least one controlled batch subresponse to the requested resource, HTTP status and Azure error code without publishing raw identifiers. For historical uncorrelated runs, state which findings may be uncertain and decide explicitly whether the limitation can be accepted. A batch with fewer or more subresponses than requests now fails the Diagnostics stage instead of silently treating missing subresponses as resources without settings; this is a deliberate target correction for malformed API output, outside the successful-source equivalence claim.
3. **Missing projections and scope:** verify non-empty Policy and Defender Recommendations rows and Arc SQL numeric `vcores` using a suitable safe environment or faithful sanitized fixtures. Exercise include/exclude precedence and parent-group traversal with exact requested, resolved and contributing subscriptions. Record absent scenarios as open rather than marking them passed from empty results.
4. **Real artifacts and privacy:** inspect generated XLSX, JSON, CSV, SARIF and stdout from a built CLI on the supported platforms. Assert subscription-ID redaction across formats where promised, document SARIF identity exposure, and check Windows ACLs on unredacted local reports. Record sensitive artifacts only in the ignored local evidence bundle.
5. **Maintenance workflows:** on a controlled test branch or manual dispatch, check both the no-change and proposed-change paths for dependency and rule refresh. Verify that no workflow bypasses protected-branch review, proposed commits preserve source pins and use bot attribution, and required checks run on the resulting PR. Do not use a passing CI run as proof these dispatch paths ran.

For each check, record the exact code revision, fixture or evidence reference, expected decision, actual outcome and remaining limitation. A new numeric coverage threshold or separate numbered gate is not a substitute for these observable behaviors.

## Later release gate

After Gate 004 and the first-release feature decision, separately verify distributable artifacts on each supported platform, clean installation, dependency and license inventory, checksums and provenance, authentication/least privilege, failure recovery, and final security/operations sign-off on the exact release SHA. Record that result as a new dated gate; do not retroactively amend Gates 001-003.

Include a controlled production-scope pilot in that release decision: explicitly approved scope and read-oriented identity, known resolved subscriptions, bounded request volume and duration, reviewed stage health/partial-result handling, secure report location and retention, and an operational rollback or stop procedure. Query-style POST requests may be read-oriented; evaluate actual endpoint semantics rather than treating HTTP verb alone as proof of a write.
