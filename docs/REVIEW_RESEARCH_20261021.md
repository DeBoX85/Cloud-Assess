# Development practice research, in progress

This is a research checkpoint for the expanded audit, not its final conclusions or authority to change gates. Complete owned-code reading and historical QA reconciliation remain unfinished. Repository observations and recommendations below are our assessment, not claims that a named framework has certified Cloud Assess.

## Primary guidance

Go's [security guidance](https://go.dev/doc/security/best-practices), retrieved2026-10-21, recommends source and binary vulnerability scanning, reviewed/tested updates, fuzzing, race detection and vet. Most are already implemented here. Preserve them; improve retained scan metadata and execution coverage rather than adding duplicate checklists. A passed historical scan cannot clear an advisory discovered later. Race detection only sees exercised paths. Review candidate packages separately from source scans before release.

GitHub's [secure workflow guidance](https://docs.github.com/en/actions/reference/security/secure-use) supports minimum token permissions, immutable action pins and protection from untrusted workflow input/code. Existing pinned actions and read-oriented gates are worth retaining. Any caching or evidence-upload proposal needs a separate review of PR trust, permissions, sensitive data and byte conservation; no workflow refresh is authorised by this document.

[NIST SSDF1.1 final](https://csrc.nist.gov/pubs/sp/800/218/final) describes security practices integrated into the development lifecycle and prevention of recurring root causes. The reviewed1.2publication is an initial public draft, not a basis for claiming final1.2compliance. [SLSA1.2](https://slsa.dev/spec/v1.2/) is approved and separates source/build provenance concerns. Our SHA256/Git readback proves matching bytes; it does not establish independent human approval, trusted execution or a SLSA level. Evaluate artifact attestations/SBOM verification at the already-planned packaging/readiness boundary, without release/publication now.

Google's [SRE postmortem guidance](https://sre.google/sre-book/postmortem-culture/) treats incident records and preventive follow-up as learning tools. Apply this narrowly to execution outages: record last verified remote state, at-risk local bytes, uncertain operations, recovery checks and one owned preventive action. Existing failure notes already cover many technical mistakes; an actionable incident index would make them easier to use than repeated narratives.
