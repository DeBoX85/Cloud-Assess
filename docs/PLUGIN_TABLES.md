# Canonical internal-plugin tables

Status: B3b contract before implementation, 2026-10-02. This slice supplies canonical table/report infrastructure, not plugin-stage execution or new CLI availability. [ZONE_MAPPING.md](ZONE_MAPPING.md) is the first adapter. Service health is the second design check: its six columns include a subscription ID and use a different query/row shape. Full second-adapter execution remains separate.

## Compatibility and ownership

Ordinary assessments retain schema `1.0`, the existing JSON field set and twelve report tables. Assessments explicitly constructed with plugin tables use schema `1.1` and an additive `pluginTables` field. Each plugin table has its own schema `1.0`, stable plugin/table IDs, source metadata, sheet name, description, ordered column names, data rows and explicit execution health. Column headers are metadata, not duplicated as data rows. A row owns its cells and records the associated subscription ID when one exists. This identity is retained for masking and troubleshooting, not added to the source-visible zone columns. Multi-subscription/aggregate rows may have no single associated subscription.

Metadata preserves the pinned internal plugin's name, version, description, author and license; the upstream author is provenance, not product branding. Source `ExternalPluginOutput` metadata/header/rows can be reconstructed for semantic comparison, but canonical JSON need not match the source design. Target-only version, table IDs, row identity and honest health are explicit additions. JSON/stdout expose tables; CSV and Excel share one projection. SARIF remains a primary-finding format and does not invent rule findings from arbitrary plugin cells.

The canonical builder validates then deep-copies table metadata, columns, rows/cells, warnings and error data. Repeated builds and mutation of caller/returned tables must not leak state. Final order is plugin ID then table ID; source row/column order is retained. Renderers validate the entire table set before output mutation, including direct library callers that modify public result fields.

## Health and limits

Health name equals plugin ID, records equal data rows, known statuses only. Completed data has no warnings/error; completed-with-warnings requires warnings and no error; failed requires error and may retain healthy rows; skipped has no data/error. Empty complete data is distinct from failed/skipped empty data. Requested failed/skipped tables still render a header and health evidence. Plugin/table health is included after ordinary stages on Assessment Status. The canonical builder folds failed/skipped table health into partial completeness and warnings into complete-with-warnings, preserving an existing critical failure. Renderers reject a manually altered result that conceals that health. Existing application partial exits are exercised with synthetic canonical results; real plugin-stage/CLI integration remains a separate acceptance boundary.

Plugin and table IDs are lower-case ASCII labels beginning with a letter, at most 64 characters, using letters/digits/hyphens. CSV keys use `plugin_<plugin-id>_<table-id>`, never API/YAML text as a path. Reject duplicate keys and Unicode-case-fold-equivalent Excel sheet collisions, including twelve reserved core sheet names, using the same EqualFold relation as pinned Excelize. Sheet names are nonempty, at most 31 UTF-16 units, with no Excel-reserved characters, control characters or leading/trailing apostrophe. No automatic truncation/renaming.

Safety ceilings: 64 tables, 64 columns/table, 65,536 rows/table, 262,144 aggregate rows, 16 MiB aggregate UTF-8 table text (cells, metadata and health messages) and 32,767 UTF-16 units/cell. Metadata text has separate bounds and valid UTF-8 requirements. These are application safety ceilings, not observed Azure maxima or representative volume certification. Reject invalid row widths, missing/duplicate columns, invalid UTF-8 and disallowed XML control characters. No silent cell/row truncation. Large/error-containing future adapters must return honest health if projection cannot meet this contract; do not drop data and claim complete.

## Privacy and human formats

Mask known subscription IDs everywhere in plugin human-output cells and rendered health text, using valid row/core identities and resolved/requested scope, including embedded links and case variants. Infer additional IDs from subscription-qualified paths/text. JSON masking retains its whole-serialized-result replacement (including descriptions) and learns row identities explicitly. Human masking has a 4,096-distinct-ID ceiling and controlled pattern-construction errors: fail before file replacement rather than panic or fall back to unmasked text. This opt-in plugin bound does not change ordinary table projection or the existing JSON masking limits. Descriptions remain canonical JSON metadata; this slice does not add them as human-report cells. Source values remain unchanged in unredacted canonical data. CSV keeps formula-as-text protection; Excel uses string cells for plugin values and creates no plugin formulas/hyperlinks from API text. Verify actual XLSX values/formulas and CSV bytes rather than only table counts. Existing privacy, file replacement and multi-file nontransactional limits still apply.

## Acceptance, evidence and rollback

Literal zone and service-health-shaped fixtures cover all metadata, columns and cells, empty/failed/skipped/partial health, identity/masking, source-visible header/row reconstruction, repeat/build isolation, schema/default compatibility, invalid identities/sheets/widths/bounds and renderer rejection before replacement. Read back actual JSON/stdout-equivalent bytes, every plugin CSV cell and actual XLSX cells/formulas, raw and masked. A compiling privacy or validation mutation must fail a named assertion and then be restored. Existing exact-head native Linux/Windows jobs remain mandatory; no live call is needed or claimed.
